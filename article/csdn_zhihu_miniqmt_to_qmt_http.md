# MiniQMT 权限收紧之后，散户量化怎么办？我把 QMT 策略环境改成了一个本地 HTTP API

> 关键词：QMT、MiniQMT、xtquant、散户量化、Python、HTTP API、程序化交易
>
> 本文只讨论软件架构与接口工程，不构成投资建议，也不代表任何券商的权限政策。MiniQMT/QMT 是否可开通、是否可用于程序化交易、需要哪些报备，请以你的开户券商、交易所和监管要求为准。

## 一、真正麻烦的不是“策略不会写”，而是运行环境被切断

过去很多个人量化用户喜欢 MiniQMT，一个重要原因是：策略可以在自己熟悉的 Python 环境里跑，再通过 xtquant 一类接口连接客户端。研究、回测、数据库、机器学习、Web 服务、消息队列，都可以放在外部工程里。

但 2026 年之后，一些用户开始遇到更现实的问题：MiniQMT 新权限越来越难开，甚至有渠道直接提示停止新增申请。

我检索到的一个 MiniQMT 社区站点在 2026 年更新了提示：其称“接券商 A 通知”，从 2026 年 7 月 6 日起 MiniQMT 已停止新增申请，存量用户后续也可能逐步停止服务。必须强调，这是一条**社区/渠道侧信息，不是证监会统一关闭 MiniQMT 的官方公告**，不同券商的实际安排可能不同，最终应以券商通知为准。

对个人开发者来说，痛点很具体：

- 原来在 VS Code / PyCharm 里运行的策略，突然不能继续用原连接方式；
- 完整 QMT 客户端还能运行策略，但大量现有工程不想全部塞进 QMT 内置编辑器；
- 外部程序仍然需要账户、持仓、订单、成交和行情；
- 实盘程序又不能简单粗暴地让多个线程直接调用 QMT API；
- 更不希望因为迁移环境，把研究代码、数据库代码、AI 模型和交易执行全揉成一个脚本。

所以我最后没有选择“把所有策略搬进 QMT”，而是做了另一层适配：

**让 QMT 只负责它最擅长的事情——连接券商和执行 QMT API；外部工程继续用 HTTP 调它。**

## 二、先说监管背景：程序化交易不是“接口能下单就能随便跑”

中国证监会在 2024 年发布《证券市场程序化交易管理规定（试行）》，并自 2024 年 10 月 8 日起施行。规定明确了程序化交易定义、报告要求、交易监测、风险防控和系统管理等要求，其中很重要的一点是“先报告、后交易”。

所以，这个项目解决的是**工程连接问题**，不是权限绕过问题。

如果你的账户没有相应权限、没有完成应有报告，HTTP 包一层并不会让它突然“合规可交易”。券商客户端、交易权限和监管要求仍然是最外层边界。

## 三、我的思路：在 QMT 里面放一个很薄的 HTTP Bridge

架构其实很简单：

```text
外部 Python / AI Agent / Web / 研究脚本
                |
                | HTTP JSON
                v
        QMT HTTP Bridge
                |
                | thread-safe queue
                v
       QMT 模型线程定时 pump
                |
                v
    QMT account / quote / order API
```

为什么中间还要加一个队列？

因为最容易踩坑的做法，就是 HTTP Server 开几个 worker 线程，然后 worker 里直接调用 QMT API。

网络线程和 QMT 策略运行上下文不是一回事。一个更稳妥的结构是：HTTP 线程只负责接收请求，把任务放入队列；QMT 自己的定时回调每隔几百毫秒把请求取出来，在模型线程里真正调用账户、行情和交易接口。

这样，外部程序看见的是普通 HTTP API，QMT 看见的仍然是它自己的策略线程调用。

## 四、我开源了两个版本

为了兼顾“能直接用”和“能长期维护”，仓库里放了两套实现。

### 1. Lite：给只想先跑起来的人

Lite 版只有一个业务接口：

```http
POST /api
```

所有操作都放在 `op` 里：

```json
{
  "op": "quotes",
  "data": {
    "symbols": ["600000.SH", "000001.SZ"]
  }
}
```

它是单文件、标准库、无代码注释版本，适合直接复制进 QMT 编辑器，也很适合先读懂整个桥接到底做了什么。

目前支持：

- account
- positions
- orders
- fills
- quotes
- history
- order
- cancel

交易默认关闭，需要显式打开环境变量才允许下单。

### 2. Full：给想做长期工程的人

Full 版把功能拆成：

- config
- protocol
- dispatcher
- adapter
- service
- security
- http_server
- runtime

另外增加了：

- Token 鉴权；
- 每 IP 请求限流；
- CORS Origin 白名单；
- 请求体大小限制；
- 账户/持仓/订单短 TTL 缓存；
- 交易请求优先队列；
- 单笔最大数量、最大金额保护；
- `X-Idempotency-Key` 防重复委托；
- 审计记录；
- QMT 回调事件缓冲；
- 单元测试。

如果只是第一次迁移，我建议先看 Lite，确认你的券商 QMT 版本能够正常访问对应 API，再考虑 Full。

## 五、为什么 Token 不直接写死在代码里

很多个人项目为了方便，会这样写：

```python
TOKEN = "my-secret-token"
```

本地自用时似乎没问题，一旦开源就非常危险。

这次公开版本中，我把所有账户号、私有命名、固定 Token 都移除了。没有配置 Token 时，服务启动会生成随机会话 Token，并打印在本机 QMT 控制台；交易功能也默认关闭。

同时服务强制只监听：

```text
127.0.0.1
```

也就是说，它的定位不是“把券商交易接口开放到互联网”，而是“给同一台电脑里的其他程序提供一个稳定适配层”。

真要远程访问，更合理的方式通常是 VPN 或 SSH 隧道，而不是直接把交易端口暴露到公网。

## 六、浏览器也能直接测

仓库里我放了一个纯 HTML 测试页，不依赖 Node.js，不需要 npm：

1. QMT 中启动 Bridge；
2. 看控制台 Token；
3. 双击 `test.html`；
4. 填地址和 Token；
5. 选择 `positions`、`quotes`、`history` 等操作；
6. 页面直接显示 JSON 返回结果。

这对排查问题很有用，因为你可以先把“QMT Bridge 是否正常”与“你的策略程序是否正常”拆开。

## 七、这层 HTTP Bridge 能给现有量化工程带来什么

最大的价值不是“又造了一个接口”，而是**隔离变化**。

假设你原来有：

```text
策略层
  ├─ 因子
  ├─ 选股
  ├─ 风控
  ├─ AI 模型
  └─ 组合管理

基础设施
  ├─ PostgreSQL
  ├─ Redis
  ├─ Web 控制台
  └─ 消息通知
```

过去最底下直接依赖 MiniQMT/xtquant。

现在只要新增一层 Broker Adapter：

```text
Strategy -> BrokerClient -> HTTP -> QMT Bridge -> QMT
```

上层业务基本不用知道券商接口发生过什么变化。

以后哪怕再换 PTrade、其他券商 API，理论上也只需要实现新的 Broker Adapter。

这才是我认为“MiniQMT 权限变化”之后，个人量化项目最值得做的一次重构：

**不要再让策略直接绑定某一个客户端 SDK。**

## 八、几个实盘一定要注意的坑

### 1. HTTP 超时，不代表下单一定失败

外部程序发了请求，8 秒没有收到响应，只能说明“HTTP 调用没有按时确认”。它不能严格证明 QMT 没有收到委托。

因此实盘必须使用稳定的 `client_order_id` / 幂等键，再去订单列表做 reconciliation（核对），而不是超时就重新下一模一样的单。

### 2. `passorder` 调用完成，不等于成交

桥接返回 `SIGNAL_SENT`，只应该理解成信号已经提交给 QMT。最终是否受理、是否部分成交、是否完全成交，都应该通过订单/成交回报确认。

### 3. 默认只读比默认可交易更合理

开源项目不知道使用者的账户规模、券商版本和测试程度，因此默认应该拒绝交易，而不是“下载即实盘”。

### 4. HTTP 层的风控不是完整风控

Full 版有单笔最大数量/金额限制，但真正的实盘系统还应该在上层做：

- 总仓位限制；
- 单票仓位限制；
- 行业暴露；
- 日内最大亏损；
- 最大成交偏离；
- 涨跌停/停牌状态；
- 订单频率；
- 异常行情保护；
- Kill Switch。

## 九、适合哪些人

这个项目比较适合：

- 原来用 MiniQMT/xtquant，正在迁移完整 QMT 的个人开发者；
- 想让策略继续跑在独立 Python 工程里的人；
- 想用 FastAPI、Flask、AI Agent、数据库等外部系统，但又不想全部塞进 QMT 的人；
- 想研究“交易执行层解耦”的量化开发者。

不适合：

- 想绕过券商权限的人；
- 想把本地交易接口裸露到公网的人；
- 没做模拟测试就直接上实盘的人。

## 十、GitHub：先从 Lite 版开始

我把最简单、最容易阅读的 Lite 版放在 GitHub 仓库中，只有一个主要 Python 文件和一个 HTML 测试页。

建议顺序：

1. 先跑 `health`；
2. 再测 `account` / `positions`；
3. 再测 `quotes` / `history`；
4. 模拟账户验证订单；
5. 最后再决定是否启用真实交易。
